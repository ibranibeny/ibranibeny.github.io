01 / Design intentStart with the direction of the request

“Private Fabric” is not a single switch. A client reading a file from OneLake initiates an inbound request to Fabric, even though the file bytes travel back to the client. A notebook reading Azure SQL initiates an outbound request from Fabric, even though the SQL rows travel into the workspace. Network policy follows the initiating workload and documented service operation, not the business description “ingest” or “export.” This distinction prevents a common error: treating outbound protection as a universal data-loss prevention control. [14]

This guide uses an intentionally small workload: three synthetic rows in an external Azure SQL Database, a Fabric notebook that reads those rows, and a Delta dataset written beneath the attached lakehouse’s Files area. Separately, a private Windows VM uploads a three-row CSV through the workspace-specific OneLake endpoint. Spark reads that CSV to demonstrate interoperability. OneLake supplies file storage; it does not connect to SQL and execute the query on its own.

Inbound concept: who can call Fabric?

VM→Private endpoint→OneLake

Connection initiator: a client outside Fabric. The customer creates a private endpoint in the client VNet, bound to the Fabric workspace's Private Link resource. The VM resolves the workspace-specific DFS hostname to the endpoint's private IP and sends an authenticated HTTPS request.

Two separate controls: the endpoint supplies the private route; the workspace inbound policy excludes unwanted public routes. A private endpoint with public access still allowed is a dual-access configuration, not private-only access. Entra authentication and workspace/item permissions are still required.

Boundary and scope: one workspace Private Link resource belongs to one workspace, but several customer VNets can each have an endpoint to it. That route does not automatically authorize a different workspace or create a reverse tunnel from Fabric into the VNet. [3]

Outbound concept: what can Fabric call?

Notebook→Managed endpoint→Azure SQL

Connection initiator: the Fabric workload. For this Spark scenario, Fabric creates and manages the endpoint in its own managed network. The SQL owner approves that endpoint request; Fabric shows both provisioning Succeeded and connection Approved.

Two separate controls: the managed endpoint supplies approved private connectivity; workspace outbound protection applies deny-by-default to supported operations. An MPE alone does not establish that all other egress is blocked. SQL public access, TLS and SQL permissions remain separate controls.

Workload-specific mechanism: Spark uses managed endpoint exceptions; Data Factory uses data connection/gateway rules. A customer VM's NAT, SQL private endpoint or DNS zone is not automatically the egress route for Fabric Spark. [10] [12]

A private endpoint establishes a private route to a particular service. It does not authenticate the caller, grant workspace access, create a SQL user, authorize table reads, or automatically disable a service’s public interface. Conversely, a valid token and table permission do not provide a route through a firewall. The acceptance criteria therefore separate DNS, transport, identity, authorization, and policy enforcement. 02 / Control planes and data planesTwo private paths, not one reverse tunnel

Follow a OneLake upload

  1. The VM obtains a Microsoft Entra token with the Storage audience. Its system-assigned managed identity must separately have the necessary Fabric authorization.
  2. The VM resolver looks up the workspace-specific DFS hostname. Through the linked private DNS zone, the answer resolves to the Fabric private endpoint’s private address. Record the actual answer privately; public evidence should show only a sanitized private-address classification.
  3. The VM opens TLS over TCP 443, preserving the service hostname for certificate verification. Azure Private Link delivers the request to the workspace service.
  4. Fabric evaluates the supported operation, inbound network policy, token, and data permission. A successful write followed by a byte-for-byte readback is stronger evidence than a portal page loading.

Follow a SQL read from Spark

  1. Spark runs in Fabric’s managed VNet. This is not VNet injection into the subnet that hosts your VM; your customer route table, DNS-zone link, and NAT gateway do not automatically govern the Spark cluster.
  2. The notebook resolves the normal SQL logical-server hostname through Fabric-managed endpoint resolution. It does not use the customer VM’s SQL endpoint address.
  3. The outbound request is permitted through an approved MPE to the SQL sqlServer subresource. Azure SQL validates Microsoft Entra authentication and database-level authorization.
  4. Rows return on the established session. Spark then writes Delta files to its lakehouse. The SQL endpoint does not get an unsolicited reverse connection into Fabric or permission to read OneLake.

Use SQL connection-policy-specific network requirements rather than declaring TCP 1433 the complete topology. The initial SQL handshake uses 1433; redirect configurations can require additional ports. Keep the official Azure SQL Private Link guidance alongside your route and firewall review. Disabling TLS certificate validation to work around DNS is not an acceptable correction.

03 / Scope-sensitive supportSupported does not mean every operation

The support decision has at least three dimensions: item type, networking scope, and the operation or connector in use. A supported item in the workspace Private Link list does not imply it uses Spark managed private endpoints. An outbound-supported semantic model does not become supported behind workspace-level inbound Private Link. Validate the intersection required by your design. [5] [10]

04 / Before touching a toggleCapacity, region, authority, and blast radius

Capacity and regional gates

  • Workspace Private Link: assign the workspace to a paid Fabric F SKU. P SKUs and trial capacities are not supported for this feature. Confirm the workspace’s actual assignment, not simply that an F capacity exists somewhere in the tenant. [4]
  • Outbound access protection: also requires an F capacity; F trials and other capacity types are excluded. This lab uses F4 as a small demonstration capacity, not as a production sizing recommendation. [10]
  • Standalone managed private endpoints: the MPE overview includes Fabric trial capacities. That narrower allowance does not override the paid-capacity prerequisites of the combined Private Link plus OAP scenario. [7]
  • Two regional checks: both the tenant home region and assigned capacity region must support Fabric Data Engineering for MPE availability. Check the current regional availability page and any workload-specific exceptions. The managed-VNet page has older named-region restrictions; do not let a general availability statement silently override an explicit limitation. [19] [9]
  • No relocation shortcut: the MPE overview does not support workspace migration across capacities in different regions. Choose an appropriate region before building endpoint dependencies.

Workspace private endpoint hostnames use the workspace GUID without hyphens, followed by .z, then its first two characters. The suffix chooses the service. GUIDs in the OneLake URL path retain their hyphens. Using the “cleaned” hostname identifier as the path identifier is a subtle but avoidable failure. [3] [18]

# Synthetic identifiers, not the lab's identifiers.
$workspaceId = '12345678-1234-4234-8234-1234567890ab'
$lakehouseId = '87654321-4321-4321-8321-ba0987654321'
$compact = ([guid]$workspaceId).ToString('N')
$prefix = $compact.Substring(0, 2)
$apiHost = "$compact.z$prefix.w.api.fabric.microsoft.com"
$dfsHost = "$compact.z$prefix.dfs.fabric.microsoft.com"
$oneLakeFile = "https://$dfsHost/$workspaceId/$lakehouseId/Files/vm-baseline.csv"

Resolve-DnsName $apiHost
Resolve-DnsName $dfsHost
Test-NetConnection $dfsHost -Port 443

# Expected hostname shape:
# 123456781234423482341234567890ab.z12.dfs.fabric.microsoft.com

The other workspace suffixes include c.fabric.microsoft.com, onelake.fabric.microsoft.com, and blob.fabric.microsoft.com. These are not five interchangeable aliases for every API. Use the hostname appropriate to the service and supported operation. Warehouse and SQL analytics endpoints have a different connection-string shape; retrieve their service-provided workspace Private Link connection string rather than constructing one from an unrelated OneLake URL. [5]

A linked private DNS zone supplies private answers only to clients using that resolution path. For hybrid networks, route DNS queries through the approved Azure resolver/forwarder and validate the applicable conditional-forwarding design. Test both a private client and a genuinely external client, without a VPN, private resolver, proxy, or cached answer that would invalidate the comparison. A zone for one workspace may cause unresolved names for another workspace unless documented DNS fallback behavior is configured. Fallback changes resolution, not authorization or network policy. [3]

Three token audiences, three separate jobs

  • Fabric REST: a token for the Fabric service, with the required delegated scope or supported application identity and Fabric permissions. The endpoint is api.fabric.microsoft.com, not Microsoft Graph.
  • OneLake DFS/Blob: a Storage-audience token, conventionally https://storage.azure.com/. A Fabric management token is not a substitute. OneLake authorization still applies to the principal. [18]
  • Azure SQL: SQL-compatible Microsoft Entra authentication, with SQL’s https://database.windows.net/ resource context. The documented Spark connector can obtain automatic Entra authentication for the signed-in execution context. Do not log the resulting token. [16]

notebookutils.credentials.getToken documents specific audiences such as Storage, Power BI, Key Vault, and Kusto—not a general promise of SQL token acquisition. Do not invent a SQL audience alias. Direct MSAL or Azure Identity code that reaches the public Entra login endpoint is also not a safe fallback in a Spark session with OAP enabled: public login traffic is explicitly among the blocked examples. The preinstalled connector avoids an unnecessary package download, but authentication must still be validated under Deny. [17] [12]

06 / Procedure ACreate an isolated, inspectable foundation

Step 1 — Declare the allowed change set

Create a new resource group for the customer network and SQL resources. Record its ownership, region, expiry, intended SKUs, and cleanup plan. Use a new dedicated Fabric capacity and workspace rather than moving an existing business workspace or modifying its endpoints. Record the pre-change communication policy and feature-gate settings. Keep the approved lab identities and identifiers in private operational records, not in this site.

The customer network contains a VM subnet, a private-endpoint subnet with sufficient free addresses, and a correctly named AzureBastionSubnet sized for the selected Bastion SKU. A sample VNet address space is 10.40.0.0/16; it is illustrative, not a prescription for a network that may overlap your environment. Reserve at least ten addresses per Fabric workspace endpoint: Microsoft currently creates five IP members per workspace-level Private Link, and explicitly recommends future headroom. Include normal Azure subnet address reservations in your sizing. [4]

Step 2 — Deploy the client network without public VM exposure

  1. In Azure, create the VNet and subnets in the selected resource group. Review address overlap and applicable network policies before creation.
  2. Create the private Windows VM with no public IP and no public inbound ports. Enable its system-assigned managed identity for the OneLake test.
  3. Deploy Bastion for administrative access. Use the current Bastion NSG requirements for the chosen SKU rather than copying arbitrary NSG service-tag expressions.
  4. If the VM requires public outbound access for administration or dependencies, associate an explicitly approved NAT gateway. NAT provides source translation, not a destination allowlist; use the organization’s egress controls if destination restriction is required.
  5. Review the resource group’s actual resources and each deployment operation. A portal form submission or partially successful ARM deployment is not a successful foundation.

NSG rules must distinguish IP prefixes from supported service tags and obey platform restrictions. In the observed lab, the initial base ARM deployment failed because platform tags were misused. Corrected ordinary IP rules and completion of missing resources through ARM produced the later working foundation. That history must not be rewritten as an initially successful deployment. The repair is evidence of diagnosis, not a reusable instruction to bypass network controls.

Step 3 — Create and verify capacity, workspace, and lakehouse

  1. Create the approved pay-as-you-go Fabric F capacity in the verified region. Leave reservations, autoscale, and paid overage features out of this small lab unless separately approved.
  2. Wait for the capacity resource to exist and become available. Record its SKU and provisioning state; do not infer success from closing the creation blade.
  3. In Fabric, create a dedicated workspace. Open Workspace settings → Workspace type or the current capacity-assignment blade and assign the new F capacity.
  4. Create a lakehouse and a notebook in that workspace. Attach the lakehouse as the notebook’s default lakehouse. Inventory item types to ensure no unsupported semantic model or deployment-pipeline assignment is introduced.

The observed capacity creation attempt in the portal did not create the resource; a later ARM deployment succeeded. Capture the resource that actually exists and label the sequence truthfully. A narrow baseline before Deny is reasonable for a synthetic, isolated lab, but it is a temporary testing state. Do not load sensitive production data while both public defaults remain Allow.

07 / Procedure BWire customer-network access into one workspace

Step 4 — Create the workspace private link service

In Azure, open Deploy a custom template → Build your own template in the editor. Use the documented resource type and API version below within a valid ARM deployment template. The resource is global; that does not relocate the workspace or turn it into a globally available compute capacity. The properties bind the resource to the tenant and one workspace. Enable Show hidden resources if the PLS is not visible in the resource-group list. [4]

{
  "type": "Microsoft.Fabric/privateLinkServicesForFabric",
  "apiVersion": "2024-06-01",
  "name": "<workspace-pls-name>",
  "location": "global",
  "properties": {
    "tenantId": "<tenant-id>",
    "workspaceId": "<workspace-id>"
  }
}

Check the resulting resource’s ID and provisioning state. Do not confuse this service-specific Fabric resource with a generic Microsoft.Network/privateLinkServices resource behind a customer load balancer. A workspace has its own PLS; multiple approved client VNets can have separate endpoints to that same workspace. A PLS for Workspace A is not a tunnel to Workspace B. [3]

Step 5 — Create the customer private endpoint and DNS zone group

  1. In Azure Private endpoints → Create, select the new resource group and the same region as the client VNet.
  2. On Resource, select Microsoft.Fabric/privateLinkServicesForFabric, the new PLS, and target subresource workspace.
  3. Select the approved private-endpoint subnet. Confirm available address headroom for the five current members and future growth.
  4. Enable private DNS integration with privatelink.fabric.microsoft.com. Check the zone group, its generated records, and the VNet link after deployment.
  5. Verify connection approval and provisioning, then inspect the NIC’s actual IP configurations. Do not hand-author only one DNS record because one initial test happens to work.

A customer private endpoint’s IP address is a routing destination, not the application connection string. Use the normal documented workspace hostname over TLS. Do not connect to a raw IP or to a privatelink alias to evade certificate-name errors. If your network uses a custom DNS server, confirm it can resolve the Azure private zone through the approved forwarding path before continuing.

Step 6 — Validate a real OneLake write before restricting inbound

Connect to the VM through Bastion. Run the FQDN algorithm in Chapter 05 using private local values and check both the workspace API and DFS answers. Obtain a Storage-audience token through the VM’s system-assigned managed identity using the supported identity mechanism in your chosen SDK or Azure tooling. Keep the token in memory; do not print it, copy it into browser developer tools, or store it in a screenshot.

Authorize that identity in the isolated Fabric workspace/lakehouse for the intended file operation. Use the OneLake-compatible DFS client to create Files/vm-baseline.csv, append the UTF-8 bytes at position zero, flush to the exact byte length, and read the file back. The request sequence below is a protocol sketch, not a token-bearing executable script. Parent directories must already exist or be created through the supported API. [18]

PUT https://<workspace-dfs-host>/<workspace-id>/<lakehouse-id>/Files/vm-baseline.csv?resource=file
Authorization: Bearer <in-memory-storage-audience-token>
x-ms-version: 2021-06-08

PATCH https://<workspace-dfs-host>/<workspace-id>/<lakehouse-id>/Files/vm-baseline.csv?action=append&position=0
Content-Type: application/octet-stream
Body: <synthetic UTF-8 CSV bytes>

PATCH https://<workspace-dfs-host>/<workspace-id>/<lakehouse-id>/Files/vm-baseline.csv?action=flush&position=<byte-length>

GET https://<workspace-dfs-host>/<workspace-id>/<lakehouse-id>/Files/vm-baseline.csv

# Supply the same required authentication/version headers on every request.
# Compare SHA-256 of the source byte array with the downloaded byte array.

Do not compare only the number of characters: UTF-8 byte length can differ. Record row count separately from header count, response status, and hash equality. The observed VM test uploaded 152 bytes containing three data rows, resolved a private address, and returned an identical readback hash. It ran before inbound Deny; therefore it proves the private route and identity worked, not that the public route was blocked.

08 / Procedure CPrepare external Azure SQL without a public back door

Step 7 — Create the SQL server and administrative private route

Create an Azure SQL logical server and a small database in the new resource group. Select the approved SQL service tier, configure Microsoft Entra administration, and enable Entra-only authentication for this design. Set the logical server’s publicNetworkAccess to Disabled. Do not add “allow Azure services” or a broad public firewall range to make a failed test pass. This SQL resource is external to Fabric and must not be confused with Fabric’s own SQL database item.

Create a second customer private endpoint to the SQL logical server, targeting sqlServer, with privatelink.database.windows.net DNS integration for the VM VNet. This endpoint exists for private SQL administration and VM-side tests. It does not satisfy Fabric Spark connectivity; the Fabric MPE in the next chapter is an independent connection. Verify SQL public network access remains disabled after creation.

Step 8 — Seed three synthetic rows and authorize only a reader

From the VM’s approved SQL client, connect using <server-name>.database.windows.net, encryption enabled, and certificate validation enabled. Verify the private DNS answer first. Connect to the intended database rather than assuming master. An authorized data owner can create the following disposable table; the notebook identity needs SELECT on that table, not SQL administrative ownership.

-- Run once in the dedicated lab database as an authorized data owner.
CREATE TABLE dbo.NetworkLabSample (
    SampleId int NOT NULL PRIMARY KEY,
    Category nvarchar(32) NOT NULL,
    Quantity int NOT NULL
);

INSERT INTO dbo.NetworkLabSample (SampleId, Category, Quantity)
VALUES (1, N'Synthetic-A', 10),
       (2, N'Synthetic-B', 20),
       (3, N'Synthetic-C', 30);

-- Substitute the approved Microsoft Entra principal locally.
CREATE USER [fabric-lab-reader] FROM EXTERNAL PROVIDER;
GRANT SELECT ON OBJECT::dbo.NetworkLabSample TO [fabric-lab-reader];

SELECT COUNT_BIG(*) AS ExpectedRows FROM dbo.NetworkLabSample;

Resolve the exact execution identity before granting the user. The SQL data owner may need appropriate Microsoft Entra directory-resolution configuration to create an external principal; follow the official Azure SQL Entra configuration guide, rather than expanding directory permissions blindly. Interactive notebook, scheduled job, API-triggered run, and service-principal execution can have different identity semantics. Capture the runtime mode in the test record and repeat authorization testing when it changes.

Actual lab privilege exception: the notebook executed as the demo user configured as the SQL server's Microsoft Entra administrator. A separate SELECT-only reader was not created or validated. The least-privilege example above is a recommended improvement, not an executed lab step. Administrative SQL rights are not required merely to read a table, and the connectivity pass does not prove least-privilege authorization.

09 / Procedure DFabric-managed egress to SQL

Step 9 — Request the Fabric-managed private endpoint

Open Workspace settings → Network security or the current managed private endpoint blade. Select Create, provide a descriptive name, paste the SQL logical server resource ID, and select sqlServer. Add an approval request describing the isolated lab and exact target. Never point the resource ID at the database child, the customer SQL PE, or the customer NIC. [8]

The equivalent documented Fabric REST shape is below. It requires workspace Admin; delegated callers need Workspace.ReadWrite.All. A service principal or managed identity is supported by this API, subject to Fabric identity configuration and authorization. The REST API creates the request; it does not approve it on the SQL owner’s behalf. [23]

POST https://api.fabric.microsoft.com/v1/workspaces/<workspace-id>/managedPrivateEndpoints
Content-Type: application/json
Authorization: Bearer <in-memory-fabric-token>

{
  "name": "mpe-lab-sql",
  "targetPrivateLinkResourceId": "/subscriptions/<subscription-id>/resourceGroups/<lab-rg>/providers/Microsoft.Sql/servers/<sql-server-name>",
  "targetSubresourceType": "sqlServer",
  "requestMessage": "Approved isolated SQL-to-OneLake lab; reader access only."
}

Step 10 — Approve the matching request at Azure SQL

  1. As the authorized SQL resource owner, open the logical server’s Networking → Private access page.
  2. Inspect the pending private endpoint connection. Match the intended request and target with your private change record; do not approve every pending request.
  3. Approve the specific Fabric request and provide an appropriate justification.
  4. Refresh the Fabric managed-endpoint view until both provisioningState = Succeeded and connectionState.status = Approved are present. A Succeeded provisioning state with Pending approval is not usable connectivity.

The first managed-network Spark session can require a cold start. The managed-VNet documentation describes approximately three to five minutes for on-demand custom-pool startup after starter pools no longer apply. Treat that as an indicative startup interval, not an SLA. If endpoint creation actually fails, inspect the service error and documented support route; do not repeatedly delete and recreate during provisioning. After MPE deletion, the overview instructs waiting at least fifteen minutes before recreating one to the same target. [9] [7]

10 / Procedure EChange policy without silently reopening the other direction

The workspace network communication API is a Fabric REST API, not Microsoft Graph. Its PUT operation replaces the policy. Omitted settings revert to defaults, and an omitted defaultAction defaults to Allow. A one-direction example copied into a live workspace can therefore undo the restriction in the other direction. The API reference explicitly instructs callers to GET first and send the full policy. [21]

Step 12 — Snapshot, merge, conditionally write, read back

  1. Call GET /v1/workspaces/<workspace-id>/networking/communicationPolicy. Retain the complete current policy and ETag in the private change record.
  2. Modify only the intended property in a copy. Preserve both inbound and outbound settings explicitly. Preserve applicable additional policy fields returned by the service according to the current schema.
  3. Use If-Match with the quoted ETag in the PUT. If another administrator has changed the policy, stop, GET the new policy, and reconcile; do not automatically retry without concurrency protection.
  4. GET again, compare the full response with the intended policy, and record the request time. Connector/gateway exception rules have their own APIs and should be independently snapshotted where applicable.

Step 13 — Apply outbound restriction first and revalidate

For a controlled migration from the baseline, set outbound Deny while preserving the inbound value you actually read. Alternatively, use the current workspace Outbound access protection → Block outbound public access control. Leave Git integration blocked unless an explicit business exception is approved. Wait for propagation; Microsoft documents up to fifteen minutes. End the earlier Spark session and run fresh positive and negative tests before proceeding. A preexisting TCP connection or cached token can conceal a new-session failure. [11]

After the private VM route works, select the workspace’s inbound setting for connections from selected networks and workspace-level private links, or set inbound Deny through the full-policy API workflow. This private-only lab should not add public-IP exceptions. Preserve outbound Deny. Microsoft documents up to thirty minutes for inbound policy propagation. Record the last known public baseline and the first denied request after the policy change. [4]

There is a deliberate control-plane nuance: workspace network settings do not restrict the workspace communication-policy API in the same way they restrict supported workspace data operations. Tenant-level network restrictions still apply. The setup documentation also describes endpoint-specific access conditions. Plan the documented administrative recovery path in advance; do not use the policy API or a tenant admin API as the “public data access must fail” test. [5]

12 / Alternative architectureData Factory uses connection and gateway rules

If the requirement is a Data Factory pipeline, Copy Job, or Dataflow Gen2 rather than Spark code, design a different outbound route. Microsoft’s Data Factory OAP article explicitly states that managed private endpoints are not the allowlist mechanism for Data Factory workloads. Configuring the Spark SQL MPE does not make a Copy activity’s cloud SQL connection private. [15]

  1. Choose the supported runtime path. For a SQL server with public access disabled, use a connector-supported virtual network data gateway or on-premises data gateway with a real private route and correct DNS to SQL. Verify current connector, authentication, capacity, region, and gateway compatibility before deploying anything.
  2. Verify the gateway route independently. A gateway hosted in or connected to the customer network needs SQL private endpoint resolution, network reachability, and its own SQL identity. It does not inherit the notebook’s managed endpoint or its user token.
  3. Create the actual connection. In Manage connections and gateways, bind the supported SQL connector to the intended gateway and database with the approved credential method. Test the connection before using it in an activity.
  4. Enable OAP and configure narrow rules. For endpoint-granular cloud connectors, keep the connector category Blocked and add only the required endpoint exception. Setting SQL Server broadly Allowed can allow all SQL Server endpoints, not just your lab server.
  5. For gateway rules, permit only the approved gateway. An allowed gateway can reach the sources accessible through that gateway. This is broader than a per-table rule, so constrain gateway membership, connection permissions, network routes, and SQL authorization separately.
  6. Bind the activity to the verified connection. Run a synthetic copy and a negative test with a nonapproved destination. Check every activity; Teams and Outlook activities, internal workspace staging, and certain cross-workspace destinations have documented limitations.

Allowlisting is permission, not transport. A cloud connector rule can allow a destination while that connection still uses a public endpoint. Only a correctly selected private network/gateway path plus target-side network configuration makes the SQL connection private. Neither a rule nor a gateway grants SQL SELECT by itself.

The Fabric portal does not currently support configuring data connection rules when Private Link is enabled at either the tenant or workspace scope. Use the documented Get Outbound Cloud Connection Rules, Set Outbound Cloud Connection Rules, Get Outbound Gateway Rules, and Set Outbound Gateway Rules APIs as appropriate. Read each current schema and preserve existing rules; these are separate from the communication-policy document. [10] [13]

This guide does not claim the gateway alternative was deployed or tested. It is an architecture branch with additional infrastructure and billing considerations, not a hidden dependency of the demonstrated notebook route. Do not add a gateway or storage staging resource to the lab merely because the original workload used Spark successfully.

Three data-movement cases that look similar but differ

  • OneLake A → OneLake B server-side copy: the OneLake OAP article describes an outbound call from the source workspace to the target workspace. The source’s outbound exception must permit the target.
  • Azure Storage → OneLake copy from URL: the destination OneLake workspace calls the source storage account. Its OAP rule must allow that source. Match Blob versus DFS connector rules to the actual endpoint family.
  • OneLake → Azure Storage copy from URL: the destination storage service calls into OneLake. OAP on the source workspace does not block that inbound read. Inbound protection and authorization are essential.

A caller with legitimate data access from an approved private client can also read data and send it elsewhere using that client’s own network. Workspace OAP is not a firewall on the VM, a clipboard policy, or a substitute for least privilege, sensitivity controls, endpoint protection, and auditing. This residual risk should appear in the threat model rather than being concealed by a “fully private” label. [14]

Shortcut chains are evaluated hop by hop: if A points to B and B points to C, permit A→B and B→C where required. An A→C permission does not repair a missing intermediate relationship. External ADLS/Blob shortcuts have the explicit MPE limitation already noted; separate Spark access to ADLS through an MPE is not evidence that the shortcut service uses the same route. This SQL-focused lab deploys no external Azure Storage account.

15 / Operate with reversible boundariesRollout, rollback, and safe shutdown

Rollout gates

Gate one is inventory and approval: supported items, paid F assignment, regional eligibility, two explicit tenant feature gates, and the allowed resource set. Gate two is private transport: customer PE and DNS, SQL public access disabled, MPE approved, and data authorization. Gate three is the observed baseline. Gate four is outbound Deny with a fresh positive SQL test and negative public test. Gate five is inbound Deny with private success and public failure. Production data should not enter the workspace before the intended enforcement and recovery gates pass.

For a new production design, prefer building approved exceptions and dependencies before onboarding workloads, rather than leaving public defaults open for an extended migration. The temporary Allow baseline here is solely for troubleshooting synthetic data in an isolated lab. Record the owner and deadline for removing that temporary state. Monitor capacity consumption while waiting for policy propagation; repeated idle sessions can outlive the actual tests.

Rollback is not “set everything to Allow”

  • Retain the original full communication policy and exception-rule snapshots. On rollback, GET the current policy, reconcile concurrent edits, and conditionally restore only the approved change while preserving the other direction.
  • Keep the SQL server’s public network access Disabled. A Fabric issue is not authorization to reopen a database publicly.
  • If outbound Deny breaks an essential operation, pause the affected job and diagnose. Any temporary relaxation must be explicitly approved, narrow, time-bounded, and followed by the same negative tests.
  • Keep the documented admin recovery route available. Workspace policy API availability is scope-dependent; tenant public blocking has a much larger blast radius and is intentionally outside the main rollout.
  • Never remove unrelated endpoints, workspace items, tenant gates, or resource groups to “restore defaults.” Shared tenant settings need separate review and ownership even when the lab originally enabled them.

Cleanup in dependency order

  1. Stop notebook sessions, scheduled jobs, and any new data writes. Export only sanitized evidence and confirm there are no business dependencies.
  2. Remove temporary test role assignments and contained SQL test users when no longer needed. Delete only the disposable test data and dedicated items approved for cleanup.
  3. Delete the lab Fabric MPE and verify its target-side connection is removed or disconnected. If recreating it later, respect the documented fifteen-minute wait.
  4. Delete the dedicated workspace/items or retain them according to the approved plan. An active workspace Private Link Service can block workspace deletion: inspect the service response and plan removal of that service and its endpoint without losing the administration path. Any temporary network relaxation needs explicit approval and must be limited to the disposable workspace. Understand workspace soft-delete retention before assuming storage billing ends.
  5. Pause or delete the dedicated F capacity only after dependent content is no longer needed. Verify the resulting state rather than assuming clicking Pause succeeded.
  6. Remove only the customer lab resource group after reviewing its contents. Verify no dedicated Bastion, NAT gateway, public IP, private endpoint, SQL database, disk, or DNS zone remains billable.
  7. Reconcile Azure Cost Management after billing latency and record residual retention or settlement charges. Do not promise a zero bill immediately after stopping compute.

  7. Prove private data and administration paths before separately enabling tenant Block public internet access. Retest management access and supported workload operations after propagation; keep a reviewed rollback path.

The tenant and workspace DNS/service scopes can coexist, but coexistence does not collapse them into one policy. For a corresponding workspace, its workspace-specific private link can take precedence in resolution when both are present in the same VNet. Conversely, a workspace endpoint alone does not provide private access to tenant capacity-management resources.
